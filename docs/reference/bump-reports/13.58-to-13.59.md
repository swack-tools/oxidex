# Bump exercise: ExifTool 13.58 -> 13.59

Tag-machinery overhaul Step 17 (R8). This is the machinery's review artifact
for one execution, not a live bump: `.exiftool-version` still reads **13.59**
before and after this run. ExifTool 13.60 does not exist upstream (13.59 is
the newest published release, and it is what this repo is pinned to), so
Step 17 was exercised against the most recent real, already-published
release delta instead — a genuine before/after, not a synthetic one.

Reproduce with:

```sh
just bump-exiftool 13.59 --dry-run --from 13.58 \
    --corpus /tmp/oxidex-exiftool-cache/combined-samples --corpus tests/fixtures \
    --min-tags 5000
```

`--dry-run` runs the full pipeline (fetch, capability-probe, `regen-all.sh`,
`verify.py`, `triage_bump.py`, the conformance double-run, the gate check)
and then reverts `.exiftool-version` and every generated file, asserting the
working tree is clean afterward — see `tools/exiftool-tables/bump-exiftool.sh`.

## Instruments and inputs

- Capability probe: `scripts/exiftool_oracle.py:resolve_tree()` against both
  the 13.58 and 13.59 source trees fetched from
  `https://github.com/exiftool/exiftool` — version string match AND
  `check_container_support()` against `combined-samples/OOXML.docx`
  (`FileType: DOCX`, confirming `Archive::Zip` under
  `/usr/bin/perl5.34`) for both trees. Both passed.
- Table regen: `tools/exiftool-tables/regen-all.sh` (tier 1 + tier 2) against
  13.59, verified with `tools/exiftool-tables/verify.py` — PASS (6,670
  fields, 44,597 enum entries, 1,072 masked fields, 6,670 hook/subdirectory
  flags, 7 `offsets_sound_until` tables, zero mismatches).
- Triage: `tools/exiftool-tables/triage_bump.py` diffing `dump_tables.pl`
  JSON for 13.58 against 13.59 (both dumps produced by the same script, same
  process, one after the other).
- Conformance double-run: `tools/exiftool-tables/conformance.py`, corpus
  `/tmp/oxidex-exiftool-cache/combined-samples` (4,238 files on disk, one
  directory per manufacturer) + `tests/fixtures`, `--recursive
  --exclude-ext sh,md,py,json`, floors `--min-files 3875 --min-tags 5000`
  (90% of the raw `find -type f` count across both corpus roots — see the
  floor-caveat note below). Both runs graded against the **same** pinned
  13.59 oracle (`--exiftool-dir` pointed at the fetched 13.59 tree
  explicitly, not the shared `/tmp` cache, so the comparison cannot pick up
  an unrelated skew). Only tier-1 tables (`binary_tables.rs`,
  `composite/tables.rs`, `filetype/tables.rs`, FITS keywords) differ between
  the BEFORE and AFTER binaries; tier 2 (MakerNote sub-directory tables, AF
  grids, the six `scripts/gen_*.pl` one-offs) was built once, at 13.59, for
  both — see "Scope of the conformance double-run" below.
- Gate check: `tools/exiftool-tables/bump_conformance_gate.py`.

### Floor caveat

`OVERHAUL_OXIDEX_PLAN.md`'s Step 17 entry names `--min-files 200 --min-tags
10000`. ExifTool's own `t/images` corpus has only 194 files, so a 200-file
floor fails spuriously against it; this run did not use `t/images` at all,
using `/tmp/oxidex-exiftool-cache/combined-samples` (4,238 files, curated
manufacturer samples) + `tests/fixtures` instead, and set floors relative to
what that corpus actually scores (`conformance.py`'s own `--recursive
--exclude-ext` walk scored 4,282 files — 90% of the raw file count is what
`--min-files` was set to, `--min-tags` left at 5,000; the run in fact saw
438,175 matched ExifTool tags before any missing/value/extra accounting).
Stated per AGENTS.md's instrument-naming rule rather than silently reusing
the plan's literal numbers against a corpus they were not sized for.

## Triage summary

115 classified deltas between 13.58 and 13.59 across the whole ExifTool
table set (not just what this corpus's files happen to exercise):

| bucket | count | share |
|---|---:|---:|
| AUTO | 42 | 36.5% |
| EXPR | 0 | 0.0% |
| COND | 10 | 8.7% |
| HAND | 63 | 54.8% |

**AUTO share: 36.5%** (42 of 115 deltas absorbed with zero source edits).

This is a small, mostly-additive point release — no module was added or
removed, and the deltas concentrate in three modules: DJI (38, almost
entirely new `Protobuf` MakerNote fields — a table shape this generator does
not emit at all, see below), Sony (14 AUTO + 10 COND + 14 HAND, four new
`Hook`-bearing fields and three changed conditional-variant tags), and Canon
(26 AUTO — pure layout/enum data, fully mechanical). The full breakdown,
including the by-module table and every individual delta, is at
`triage-13.58-to-13.59.md` (generated fresh by the reproduce command above;
not committed here since it duplicates this document's content — see the
"regenerate" note at the bottom).

**Why HAND dominates:** 38 of the 63 are DJI `Protobuf::dvtm_*` tables — new
device-specific field names/formats in tables ExifTool does not read with
`ProcessBinaryData` (they are Protobuf-encoded), which is the one shape
`codegen.py` transcribes at all (`docs/TRANSCRIPTION.md` "Honest limits").
None of these 38 are reachable through the generator regardless of how the
bump machinery evolves short of a dedicated Protobuf-table engine — they are
correctly HAND, not a machinery gap. The other 19 diff-driven HAND items are
`Sony::Tag94xx` `Hook` fields (mid-table format rewrites — Step 26) and small
layout additions on tables the generator does not emit for unrelated reasons
(Exif `Composite::Desire` arrays, one FujiFilm RAF field, one Pentax `Main`
field). Six further HAND items are **standing**, not diff-driven: the
generator-less files below.

### Standing HAND items (generator-less files)

Per `docs/TRANSCRIPTION.md` "Honest limits" — listed on every bump
regardless of whether that release touched them, and counted into the HAND

- `src/parsers/tiff/makernotes/sony/plain_tables.rs`

- `src/parsers/tiff/makernotes/nikon/settings_tables.rs`
- `src/parsers/tiff/makernotes/minolta_a100_tables.rs`

### COND deltas (10) — need a condition/dispatch (Step 23)

All 10 are in `Sony`: two changed conditional-variant tags (`Main::36944`,
`Main::37888`, `Tag9400c::42`) and seven new/changed `Condition` fields
across `Tag9050d`, `Tag9400c`, `Tag9401`, `Tag9416`. None are evaluated
today regardless of this bump — `Condition` is recorded but not run until
Step 23 lands — so these represent real, newly-arrived work, not existing
debt this release happened to touch.

| Triage classified debt (EXPR+COND+HAND) | 73 |
| **Gate: MISSING growth <= classified debt** | **PASS** (0 <= 73) |
| Group-qualified VALUE regressions | **0** |
| **Gate: zero group-qualified VALUE regressions** | **PASS** |

The BEFORE and AFTER corpus totals are in fact identical at every column
(`TOTAL 4282 438175 72 1653 11687 60001`, matched/renames/value/missing/extra)
— this specific 4,282-file corpus does not happen to exercise any of the 115
classified deltas (the DJI Protobuf devices, the Sony `Hook`/`Condition`
fields, the Canon enum changes) directly. **Say so rather than overstate it:
this delta measures as small and, on this corpus, unobservable in aggregate
conformance — an honest "little changed, here is the evidence" result, not
a demonstration of either the machinery or the release doing something
dramatic.** The triage report is still the correct instrument for what
*would* need attention if a sample exercising those specific tables existed;
the conformance run confirms the regen introduced no regression on the
corpus actually available.

## Scope of the conformance double-run

Only tier-1 generated tables (`binary_tables.rs`, `composite/tables.rs`,
`filetype/tables.rs`, FITS keywords) were rebuilt for the BEFORE (13.58)
binary; tier 2 (MakerNote sub-directory tables, Nikon AF-point grids, the
six `scripts/gen_*.pl` one-offs) was left at its 13.59 regeneration for both
binaries. This isolates tier 1's measurable contribution and keeps the
double-run's cost bounded (a full tier-1+tier-2 rebuild for the BEFORE binary
would roughly double this run's ~10 minute cost). The triage report's
classification is unaffected by this scoping choice — it diffs the raw
`dump_tables.pl` JSON, not any generated Rust — so no delta is
mis-classified by it; only the conformance *double-run's* BEFORE binary is
narrower than a fully-regenerated 13.58 tree would be.

## What ran, and what did not

Ran, against real data, in this exercise: fetch + capability-probe for both
13.58 and 13.59; `regen-all.sh` (tier 1 + tier 2) against 13.59;
`verify.py`; `triage_bump.py`; two `conformance.py` runs (4,282 files,
438,175+ matched ExifTool tags each) against the pinned 13.59 oracle;
`bump_conformance_gate.py`. Not run as part of this exercise: `just
ci-standard` or the release profile (out of scope per this step's process
rules — the orchestrator runs those centrally); a tier-2 rebuild of the
BEFORE binary (see scope note above); `t/images` (not cloned — 194 files,
below this run's corpus; `combined-samples` was used instead, see the floor
caveat).

`.exiftool-version` reads **13.59** in the commit that carries this report,
identical to before this exercise ran — confirmed via `git status
--porcelain` after the `--dry-run` invocation completed (clean) and by
`cat .exiftool-version` (unchanged).
