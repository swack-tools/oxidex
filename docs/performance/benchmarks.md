# Benchmarks

OxiDex has two benchmark instruments. They answer different questions, and
their numbers are not interchangeable.

::: warning Historical benchmark material, not beta.1 evidence
The results currently linked from [Performance](/performance/) were measured
at commit `8f04e288` for OxiDex 1.2.1. They are historical context only. A
v2.0.0-beta.1 exact-candidate-SHA benchmark receipt is pending, so this page
does not establish beta.1 performance.
:::

| Instrument | Question it answers | Where it runs | Where results go |
| --- | --- | --- | --- |
| `benches/exiftool_comparison.sh` (hyperfine, CLI wall-clock) | How does the `oxidex` binary compare with the pinned Perl ExifTool? | Locally by hand; in CI via `benchmarks.yml` on every push to `refactor/tag-machinery` | A local run rewrites `benches/benchmark_results.{md,json,log}`, which are committed. A CI run produces a step summary and a `benchmark-comparison` artifact, which are never committed. |
| Criterion (`cargo bench`) | Did an in-process code path get slower or faster? | Locally; in CI via `ci.yml`'s `metrics` job on pushes to `main` only | `target/criterion/`. From `main`, `deploy-docs.yml` publishes the reports at `/benchmarks/`. |

Neither CI job gates a merge, and neither has a regression threshold.

## Comparing against ExifTool

The script refuses to measure rather than measure the wrong thing. Before the
first number it prints an `=== instrument ===` header, generated by
`benches/instrument_check.py`, that names:

- the `oxidex` binary, its sha256, and a staleness warning if the binary is
  older than HEAD or than any dirty file;
- the ExifTool oracle. Its `-ver` must equal `.exiftool-version` (13.59)
  **and** it must pass the `OOXML.docx` capability probe. A matching `-ver`
  alone is not enough: a perl without `Archive::Zip` still prints the right
  version while every container format degrades.
- the git commit and whether the tree is dirty. A dirty tree refuses unless
  `OXIDEX_ALLOW_DIRTY_TREE=1` is set, and then the header says so.
- the machine, and the load before and after every scenario.

```bash
# 1. The shipped profile (fat LTO). The script refuses a missing or stale binary.
cargo build --release

# 2. The pinned ExifTool. Any recipe that needs it fetches the pinned release
#    into $EXIFTOOL_CACHE_DIR (default /tmp/oxidex-exiftool-cache), e.g.:
just compare-exiftool-full

# 3. A perl that can load Archive::Zip, if the default one cannot.
export EXIFTOOL_PERL=/path/to/perl

# 4. Run it: hyperfine --warmup 5 --runs 30, both commands per invocation.
./benches/exiftool_comparison.sh
```

The scenarios are:

1. **Single file.** A 112-byte JPEG stub, which really measures process
   startup, and `t/images/Canon.jpg` with `-j -a -G1`.
2. **Batch.** 1000 replicated JPEG fixtures read with `-r`. OxiDex reads them
   in parallel (rayon); ExifTool is single-threaded.
3. **Write one tag.** `oxidex -EXIF:Artist=…` against
   `exiftool -Artist=… -overwrite_original`.
4. **Format detection.** One JPEG, default text output.
5. **Corpus.** The pinned tree's 194-file `t/images` in one invocation with
   `-j -a -G1`. OxiDex runs once with rayon and once with
   `RAYON_NUM_THREADS=1`. The single-threaded run is the like-for-like,
   per-core comparison.

Useful environment variables: `HYPERFINE_WARMUP` and `HYPERFINE_RUNS`
(defaults 5 and 30), `OXIDEX_MAX_LOAD=N` (refuse above load N),
`BENCH_ENVIRONMENT` (stamped into the report), and `EXIFTOOL_CACHE_DIR`.

A run rewrites the top of `benches/benchmark_results.md`. Everything below
its `<!-- historical -->` marker is kept verbatim. Commit a new table only
from a quiet machine, and take the repository's exclusive heavy-job lock if
other work shares the host. A starved measurement reads as a regression.

The historical committed results are on the [Performance](/performance/) page;
they are not v2.0.0-beta.1 evidence.

## Criterion micro-benchmarks

```bash
cargo bench --bench parse_benchmarks        # format_detection, jpeg_segment_parsing,
                                            # tiff_ifd_parsing, full_read_metadata, ...
cargo bench --bench integration_benchmarks  # single_extraction, batch_100_jpegs,
                                            # large_file_handling, format_comparison, ...
cargo bench --bench raw_parsing_bench
just bench                                  # cargo bench --workspace
```

Reports are written to `target/criterion/report/index.html`. Use Criterion's
baselines (`--save-baseline`, `--baseline`) to compare one change against
its parent on the same machine.

`ci.yml`'s `metrics` job runs `integration_benchmarks` and `parse_benchmarks`
with `--quick`, `lto=false` and 16 codegen units. That makes the job cheaper,
but it measures a binary no release ships. Treat its reports as a trend
signal for one code path, not as a figure to quote.
